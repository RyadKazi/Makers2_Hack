# AccesU Navigation API

AccesU Navigation API is a Python and FastAPI service for calculating routes through university-authored building graphs. It applies Dijkstra's shortest-path algorithm to explicit, verified graph connections and returns the ordered route with floor transitions and map metadata.

> **Navigation is assistive.** This service does not replace a white cane, guide dog, human assistance, or an on-site accessibility inspection. A route result is not a safety guarantee. The included demonstration graph is synthetic and is not a surveyed campus map.

## Features

- Dijkstra routing over a building-level graph spanning multiple floors.
- General pedestrian, wheelchair, and visual-impairment navigation profiles. `blind_navigation` is also accepted as a compatibility profile value.
- Wheelchair constraints that exclude stairs, blocked connections, and graph facts explicitly marked inaccessible. Verified door-width and ramp-slope measurements can be checked against caller-provided thresholds.
- University-defined node IDs, coordinates, floor IDs, doors, rooms, entrances, stairs, elevators, ramps, landmarks, and verified connections.
- HTTP endpoints for route calculation, consent-gated navigation contributions, and aggregate-only administrator analytics.
- Optional startup loading from JSON for the legacy navigation routes. Versioned `/api/v1` graph, API-key, and session persistence uses PostgreSQL when configured.
- Cohort-suppressed statistical disparity detection and non-persistent hypothetical graph simulations for infrastructure review.
- Swagger UI and OpenAPI schema generated by FastAPI.

The visual-impairment profile returns ordered nodes, edge metadata, floor transitions, and available landmarks. It does not generate spoken directions. A separate guidance layer can use these verified facts to produce instructions.

### 1. Start the API

From the `ai-service` directory, create and activate a virtual environment, install dependencies, then load the synthetic example graph and start Uvicorn.

**Windows PowerShell:**

```powershell
py -3.11 -m venv venv
.\venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
$env:ACCESU_BUILDINGS_FILE = "examples/demo_building.json"
python -m uvicorn main:app --reload
```

**Linux or macOS:**

```bash
python3 -m venv venv
source venv/bin/activate
python -m pip install -r requirements.txt
export ACCESU_BUILDINGS_FILE=examples/demo_building.json
python -m uvicorn main:app --reload
```

The local base URL is **`http://127.0.0.1:8000`**. Swagger is at [`/docs`](http://127.0.0.1:8000/docs), ReDoc at `/redoc`, and the OpenAPI document at `/openapi.json`.

If `ACCESU_BUILDINGS_FILE` is not set, the service starts with an empty registry. `/buildings` returns an empty list and route requests return `404 Building not found` until a graph is loaded.

### 2. Send a route request

The example graph is synthetic. This request calculates a route from graph data in `examples/demo_building.json`; it is not a real campus route:

```javascript
const response = await fetch("http://127.0.0.1:8000/navigation/route", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    building_id: "SYNTHETIC_DEMO_BUILDING",
    start_node: "GROUND_ENTRANCE",
    destination_node: "F1_ROOM_105",
    profile: "general"
  })
});

const body = await response.json();
if (!response.ok) {
  throw new Error(body.message ?? `Route request failed (${response.status})`);
}

console.log(body.route.nodes); // Ordered university-defined node IDs
console.log(body.route.total_distance); // Sum of edge distances
console.log(body.route.floor_transitions); // Floor changes along the path
```

The API returns node IDs in traversal order, plus `node_details` with coordinates and landmarks and `edges` with connection metadata. A map can draw the route by looking up each returned node's `floor_id`, `x`, and `y` in its own floor-plan layer. Use `floor_transitions` to switch layers or show a transition. Do not draw lines across floors as if they were same-floor corridors.

### 3. Understand errors

Errors use a consistent JSON envelope, for example:

```json
{
  "success": false,
  "message": "no valid route from 'GROUND_ENTRANCE' to 'F1_ROOM_105' for wheelchair profile"
}
```

Handle `response.ok` before rendering route data. A missing building or node returns `404`; invalid JSON fields/profile and a valid request with no accessible route return `422`. See [HTTP endpoints](#http-endpoints) for the complete status behavior.

### Route request

```http
POST /navigation/route
Content-Type: application/json
```

```json
{
  "building_id": "SYNTHETIC_DEMO_BUILDING",
  "start_node": "GROUND_ENTRANCE",
  "destination_node": "F1_ROOM_105",
  "profile": "general",
  "constraints": {}
}
```

`constraints` is optional. It may contain `minimum_door_width_m` and `maximum_ramp_slope`. A measurement is used to filter a route only when its corresponding graph metadata is marked `verified: true`. Unknown measurements are not fabricated. No default door-width or ramp-slope threshold is imposed; clients can send the preferences appropriate to their user and context.

Profiles accepted by the API:

- `general`: shortest valid pedestrian path, including declared stairs.
- `wheelchair`: never uses stairs; excludes blocked and explicitly inaccessible nodes/connections. Verified width and slope data is checked when a threshold is supplied. Equal-distance choices prefer verified accessible entrance, ramp, or elevator connections.
- `visual_impairment`: shortest valid pedestrian path with ordered nodes, transitions, edges, and available landmarks. It does not generate audio instructions.
- `blind_navigation`: compatibility spelling for the same behavior as `visual_impairment`.

Example success response for the synthetic graph. The JSON below shows the core fields; actual responses also include complete `node_details` and `edges` arrays for the returned path.

```json
{
  "success": true,
  "message": "Route successfully calculated",
  "route": {
    "nodes": [
      "GROUND_ENTRANCE",
      "GROUND_CORRIDOR",
      "STAIR_G",
      "STAIR_F1",
      "F1_ROOM_105"
    ],
    "total_distance": 18.0,
    "floor_transitions": [
      {
        "from_floor": 0,
        "to_floor": 1,
        "from_floor_id": "G",
        "to_floor_id": "F1",
        "type": "stairs"
      }
    ],
    "profile": "general"
  }
}
```

The route's node IDs and transition are calculated from the graph in `examples/demo_building.json`; the distance is the sum of its edge distances. The API additionally returns Pydantic node and edge objects, including coordinates and accessibility/landmark metadata.

### Error responses

Validation and HTTP errors use `{ "success": false, "message": "..." }`. Request validation errors also include an `errors` array with field locations. Status codes:

- `404`: requested building or node is not loaded.
- `409`: node ID exists in multiple buildings and `building_id` was omitted.
- `422`: malformed request, unsupported profile, or no valid route for the selected profile.

FastAPI's built-in request validation also rejects unknown request fields and malformed values.

## Building graph data

### How the graph works

- A **building** owns one or more **floors**, each with a stable `floor_id` and display level.
- University staff place each **node** directly on its floor layout. A node includes its building/floor IDs, coordinates, type, and known metadata. Door nodes can be destinations.
- An **edge** represents a verified physical connection between two explicitly named nodes. The service does not connect nearby coordinates automatically. Edges are bidirectional by default; set `bidirectional: false` for one-way movement.
- Corridor and doorway edges must remain on one floor. Cross-floor edges must be explicitly typed as stairs, elevators, or ramps.
- Stair nodes on different floors must have distinct node IDs and share the same `staircase_connection_id`; a stairs edge connects corresponding nodes.
- Elevator edges connect elevator nodes; ramp edges connect ramp nodes. These types can cross floors.
- Edge distances must be finite and non-negative. Blocked edges and nodes are excluded from route results.

The graph describes navigation connectivity separately from the visual floor-plan drawing. This service does not ingest SVG geometry or verify a building survey. The administrator-provided graph must represent real, inspected connections.

### Graph JSON format

Use `examples/demo_building.json` as a complete schema example only. It is explicitly synthetic. A building file can contain a single building object, an array of building objects, or a wrapper object with a `buildings` array. The following is a valid, minimal, single-floor graph shape:

```json
{
  "building_id": "BUILDING_A",
  "name": "Example building; replace with surveyed data",
  "floors": [{"floor_id": "G", "level": 0, "name": "Ground floor"}],
  "nodes": [
    {
      "node_id": "G_ENTRANCE",
      "building_id": "BUILDING_A",
      "floor_id": "G",
      "x": 10,
      "y": 12,
      "node_type": "entrance"
    },
    {
      "node_id": "G_ROOM_105",
      "building_id": "BUILDING_A",
      "floor_id": "G",
      "x": 40,
      "y": 16,
      "node_type": "door",
      "is_destination": true,
      "label": "Room 105"
    }
  ],
  "edges": [
    {
      "source_node": "G_ENTRANCE",
      "destination_node": "G_ROOM_105",
      "distance": 30,
      "connection_type": "doorway"
    }
  ]
}
```

This JSON is structurally valid, but its coordinates and connection are illustrative placeholders and do not describe a real building. Replace them with administrator-provided map data before use. Every referenced node must exist, every node's floor must exist, and all edges must satisfy the model's floor-transition rules. Relevant node types are `door`, `staircase`, `corridor_intersection`, `entrance`, `elevator`, `ramp`, `room_access`, and `waypoint`. Connection types are `corridor`, `doorway`, `stairs`, `elevator`, `ramp`, `entrance`, and `other`.

The legacy navigation routes can load a JSON graph at startup and keep it in memory. Versioned `/api/v1` routes read the selected building graph from PostgreSQL when `DATABASE_URL` is configured. No public graph edit endpoint is provided; manage university graph data through an authorized administrative workflow or controlled database migration process.

## How route calculation works

The existing Dijkstra implementation uses each allowed edge's `distance` as its primary cost. It searches the whole building graph, so explicitly linked vertical transitions can participate in one route. It returns the ordered node IDs, oriented traversed edges, total distance, and transitions where the floor changes.

Accessibility filtering happens before an edge is relaxed by Dijkstra. Blocked connections are excluded for all profiles. Wheelchair routes exclude stairs and connections/nodes explicitly marked inaccessible. Optional door-width and ramp-slope constraints apply only to verified measurements. Equal-distance wheelchair routes use a secondary preference for verified accessible entrances, ramps, and elevators; that preference never makes a longer route shorter. No route is returned if the graph has no valid path.

`general` and `visual_impairment` profiles may use stairs when they are declared. Spoken instructions, wall-following guidance, map geometry checks, automatic obstruction detection, route-time estimates, and machine-learning predictions are not implemented.

## Frontend and backend integration

### Next.js / browser JavaScript

Set the browser's API base URL in your frontend configuration and make a JSON request. In production, expose only the appropriate public API URL to browser code; keep internal service URLs in server-side configuration.

```javascript
const API_BASE_URL = process.env.NEXT_PUBLIC_ACCESU_API_URL ?? "http://127.0.0.1:8000";

export async function fetchAccessibleRoute({ buildingId, startNode, destinationNode, profile }) {
  const response = await fetch(`${API_BASE_URL}/navigation/route`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      building_id: buildingId,
      start_node: startNode,
      destination_node: destinationNode,
      profile
    })
  });

  const body = await response.json();
  if (!response.ok) {
    throw new Error(body.message || `Navigation request failed (${response.status})`);
  }
  return body.route;
}

const route = await fetchAccessibleRoute({
  buildingId: "SYNTHETIC_DEMO_BUILDING",
  startNode: "GROUND_ENTRANCE",
  destinationNode: "F1_ROOM_105",
  profile: "general"
});
// Use route.node_details to map returned IDs to floor coordinates.
console.log(route.nodes, route.floor_transitions);
```

The default CORS allowlist permits `localhost:3000` and `127.0.0.1:3000`. Configure `ACCESU_ALLOWED_ORIGINS` for other frontend origins. CORS is not authentication. Keep private API keys on trusted backend callers; browser applications should call their own authenticated backend.

### Express.js server-to-server call

Keep the FastAPI base URL in the Express server's environment (for example, `ACCESU_NAVIGATION_URL`). The Express application should perform its own user authentication/authorization and send only the route request data needed by this service.

```javascript
const navigationUrl = process.env.ACCESU_NAVIGATION_URL ?? "http://127.0.0.1:8000";

app.post("/api/routes", async (req, res, next) => {
  try {
    // Authenticate and authorize req.user in Express before forwarding.
    const upstream = await fetch(`${navigationUrl}/navigation/route`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        building_id: req.body.building_id,
        start_node: req.body.start_node,
        destination_node: req.body.destination_node,
        profile: req.body.profile,
        constraints: req.body.constraints
      })
    });
    const payload = await upstream.json();
    res.status(upstream.status).json(payload);
  } catch (error) {
    next(error);
  }
});
```

For deployment, restrict network access to the internal navigation service and configure the service token. This repository has no Express application yet, so the relay above is an integration example rather than implemented Express code.

## Student path learning and accessibility analytics

This feature uses deterministic aggregation and robust statistics. It does **not** use reinforcement learning: observed paths alone do not provide actions, rewards, or feedback for an RL environment. No model is trained, and no student movement changes the official graph.

### Consent and session flow

1. The frontend obtains the disclosure from `GET /navigation/sessions/consent` and displays it before requesting opt-in. The response includes the current consent version, purpose, collected/not-collected fields, audience, retention window, and controls.
2. The authenticated Express service validates the user and explicit consent, creates a stable pseudonymous contributor reference as a 64-character HMAC hex digest, and sends `POST /navigation/sessions/start` with `X-Accesu-Service-Key` and `X-Accesu-Contributor-Ref`. Never forward a name, student ID, or raw account identifier.
3. The service returns a random `session_id`, a one-time opaque `session_token`, status, and server-enforced expiry. Treat the token as a bearer secret; keep it in Express server-side session storage or a protected `HttpOnly` session, not in logs or public URLs.
4. Send pause/resume/finish/status/events/delete calls through Express with both the service key and `X-Accesu-Session-Token`. A session can be paused, resumed, finished, and deleted by its contributor. Expired, paused, finished, invalid-consent, or unauthorized sessions cannot accept events.

`this_navigation` expires automatically after `ACCESU_SESSION_MAX_HOURS` (default 2 hours) unless explicitly finished first. `until_expiry` requires a timezone-aware `expires_at` chosen by the user and is bounded by `ACCESU_MAX_SHARING_HOURS` (default 24). A client may calculate a local end-of-day timestamp and send it, but the server validates and enforces the resulting absolute expiry. An omitted expiry is never interpreted as unlimited sharing.

The FastAPI service does not collect GPS. Each event contains the graph node sequence for validation, but the ordered sequence is discarded in the request handler. The in-memory contribution record retains the OD pair, voluntarily selected profile, approximate duration, graph-derived distance, condition context, unordered edge references, staircase IDs, and structured report counts for up to the configured retention window. Admin APIs never return session IDs, contributor references, or per-session records. A contributor can request deletion of retained records using the session token.

### Session endpoint examples

Start a session after the user has explicitly opted in:

```http
POST /navigation/sessions/start
X-Accesu-Service-Key: <server-only service secret>
X-Accesu-Contributor-Ref: <64-character HMAC hex digest>
Content-Type: application/json
```

```json
{
  "building_id": "BUILDING_A",
  "consent_given": true,
  "consent_version": "consent-v1",
  "duration_choice": "this_navigation"
}
```

For a user-selected absolute expiry, use `"duration_choice": "until_expiry"` and include e.g. `"expires_at": "2026-11-20T18:00:00+00:00"`. The API rejects missing, timezone-naive, past, or over-limit expiry values. If the consent text changes, update `ACCESU_CONSENT_VERSION`; old consent versions cannot start new sessions.

Submit one completed journey or an unsuccessful route attempt:

```http
POST /navigation/sessions/{session_id}/events
X-Accesu-Service-Key: <server-only service secret>
X-Accesu-Session-Token: <opaque token returned at start>
Content-Type: application/json
```

```json
{
  "event_id": "22de8212-9ca3-4c48-a0e7-690ad9457681",
  "origin_node": "G_ENTRANCE",
  "destination_node": "F1_ROOM_105",
  "profile": "wheelchair",
  "completed": true,
  "duration_seconds": 420,
  "node_sequence": ["G_ENTRANCE", "G_CORRIDOR", "G_LIFT", "F1_LIFT", "F1_ROOM_105"],
  "constraints": {},
  "context": "typical",
  "obstacle_reports": []
}
```

The event must use real node IDs and every consecutive pair must be joined by a graph edge allowed for the submitted profile. The server computes distance from graph edge weights; a client cannot choose a fabricated distance. For `completed: false`, send an empty `node_sequence`; this records an attempt and duration but does not claim a route was traversed. `event_id` makes retries idempotent. `context` is one of `typical`, `temporary_disruption`, `elevator_unavailable`, or `unknown`; only comparisons within matching contexts are made, and infrastructure findings require `typical` context.

Structured `obstacle_reports` contain a `report_type` and known `node_id`; no free-text personal information is stored. Supported types are `blocked_path`, `narrow_passage`, `ramp_too_steep`, `elevator_unavailable`, `uneven_surface`, and `other_difficulty`. Reports remain observations and never modify graph accessibility facts.

### Statistical method and thresholds

Each origin/destination pair is analyzed separately for `wheelchair`, `visual_impairment`, and the compatibility profile `blind_navigation`, compared to `general`. Profile groups are not merged, because their constraints may differ. For each sufficiently observed, condition-matched group the service computes medians for completed-trip duration and graph distance, session count, distinct pseudonymous contributors, completion rate, and route availability.

The default disparity rule requires all of the following:

- At least 20 sessions **and** 5 distinct contributors on each compared side.
- At least 20 completed journeys on each side for a duration/distance comparison.
- Accessibility median duration at least 1.5 times the general median.
- Accessibility median duration at least 180 seconds longer.
- At least 70% of distinct accessibility contributors have a personal median duration above the general median.

If a sufficiently observed accessibility group has no completed route attempts, it is reported as unreachable. If conditions differ, completion samples are too few, or the thresholds do not align, the comparison is inconclusive. Small groups are omitted rather than returned with low counts. These defaults are engineering thresholds, not accessibility standards; administrators can configure them through environment variables, then review them with privacy and accessibility stakeholders.

### Administrator analytics API

All `/analytics/accessibility/*` endpoints require `Authorization: Bearer $ACCESU_ADMIN_TOKEN`. The configured token grants the analytics administrator role; invalid credentials receive `403`, a missing token receives `401`, and an unconfigured admin token disables the endpoints with `503`. Administrative reads and status updates emit a stderr audit log with hashed actor/resource fingerprints; the log does not contain route paths, contributor refs, or credentials.

- `GET /analytics/accessibility/overview` returns eligible comparison count, detected disparity/unreachable counts, recommendation count, analysis window, and configured thresholds.
- `GET /analytics/accessibility/disparities` returns only threshold-qualified aggregate OD/profile comparisons. It never returns session IDs, ordered paths, or contributor refs.
- `GET /analytics/accessibility/heatmap/{building_id}` returns graph node IDs/coordinates, profile-separated route counts, disparity flags, and thresholded structured report counts. Each displayed profile cohort must meet the contributor minimum; small categories are suppressed.
- `GET /analytics/accessibility/recommendations` and `GET /analytics/accessibility/recommendations/{recommendation_id}` return aggregate review candidates, evidence, limitations, confidence, status, candidate map area, and simulated distance values where available.
- `POST /analytics/accessibility/recommendations/{recommendation_id}/status` accepts `{ "status": "under_inspection" }` (or another supported status). Statuses are process-local and reset on restart.

### Recommendation location and route simulation

For detected typical-condition disparities, the service checks whether observed general routes used a university-defined staircase. If so, it creates a **temporary overlay graph** with a hypothetical accessible vertical edge between the corresponding staircase nodes and runs the existing Dijkstra engine against that copy. It compares the current wheelchair route distance with the simulated route; the official `NavigationGraph` is never changed. If the current accessible route is unavailable, the simulation can identify a candidate connection that would make a route possible.

The candidate coordinates are the existing staircase node coordinates on each floor, with nearby explicitly connected map nodes included for inspection. The service has no wall, floor-boundary, structural, clearance, fire-egress, or construction geometry. It therefore reports a suggested area requiring a physical survey, not an installation point or a claim of feasibility. For simulation only, it reuses the mapped stair edge distance as a placeholder vertical-connection cost and labels that assumption. No travel-time saving is estimated because there is no validated time model. Repeated typical-condition obstacle reports can also create an accessibility inspection candidate once report session/contributor thresholds are met.

### Next.js heatmap and Express integration

The heatmap response can be rendered on the existing 2D floor map by mapping `node_id` to graph coordinates and using `floor_id` to select a layer. Use profile-specific counts to style normal and accessibility traffic separately; use `disparity` and `obstacle_reports` as separate evidence layers. A high traffic count alone is not an accessibility problem.

Do not put `ACCESU_ADMIN_TOKEN`, `ACCESU_SERVICE_TOKEN`, or versioned API keys in a browser bundle. A Next.js application should call its own authenticated server route, which then calls this API. That backend should verify the signed-in user and role before forwarding requests. For student contributions, the backend should present the consent disclosure, enforce the user's choice, derive the HMAC contributor reference from its authenticated account, and relay session calls with its private API key. This repository contains no frontend or application-authentication gateway.

## Learning approach and privacy boundaries

- No names, student IDs, or continuous GPS coordinates are accepted by this service. A trusted backend supplies a stable 64-hex pseudonymous reference; FastAPI HMACs it again with `ACCESU_CONTRIBUTOR_HASH_SECRET` and stores only the digest.
- Consent is explicit (`consent_given: true`) and versioned; sharing is off unless a trusted caller starts it. The user can pause, resume, finish, inspect status, and request deletion of retained contributions.
- Session tokens are random and only their hashes are stored. Session, event, service, and admin credentials are never included in API responses to administrators or application audit logs.
- Admin APIs expose aggregates only. Comparisons require 20 sessions and 5 distinct contributors per side by default; heatmap profile categories and barrier types below the cohort threshold are suppressed.
- Ordered node sequences are validated against existing graph edges and profile constraints, used to calculate distance/stair/edge aggregates, then discarded. No graph path is changed based on student observations.
- Legacy unversioned session/contribution state remains process-local. Versioned `/api/v1` session records, hashed session tokens, minimized contributions, graph data, API keys, and analysis snapshots use PostgreSQL through `data/postgres.py` when `DATABASE_URL` is configured. Ordered node sequences are discarded after validation; persisted node visits are unordered and retention-pruned. The v1 API-key rate limiter is process-local.
- Legacy admin routes use a single configured bearer token, not a university identity/RBAC integration. Versioned routes use database-managed hashed API keys with permissions, expiry, revocation, and per-key rate limiting. Protect the service network and use HTTPS through the deployment.
- The consent and route APIs do not guarantee a student-facing consent screen or device-level stop control; those must be implemented and verified in the future Express/Next.js client before real deployment.

## Reinforcement learning

Reinforcement learning is not implemented. This feature uses route validation, medians, contributor-level consistency checks, cohort thresholds, and deterministic graph-copy simulations. A future contextual bandit would require an explicitly designed action/reward loop, safeguards, human review, and evaluation before any use.

## Troubleshooting

- **`Building not found`**: confirm `ACCESU_BUILDINGS_FILE` points to readable JSON and the requested `building_id` matches it exactly. Without the variable, the registry is empty.
- **Startup validation error**: check duplicate IDs, node `building_id`/`floor_id`, edge endpoints, finite non-negative distances, and vertical edge types. Startup fails rather than serving invalid graph data.
- **`start node not found` / `destination node not found`**: verify the IDs belong to the selected building; IDs are case-sensitive.
- **No valid route**: ensure the administrator defined a continuous series of real edges. For wheelchair routes, check for stairs, blocked edges, inaccessible metadata, and configured width/slope constraints. The engine will not invent an alternative connection.
- **Browser CORS error**: add the frontend's exact origin (scheme, hostname, and port) to `ACCESU_ALLOWED_ORIGINS`, then restart the service.
- **HTTPX/TestClient import error**: reinstall dependencies with `python -m pip install -r requirements.txt` in the active virtual environment.
- **PowerShell cannot activate the environment**: use `venv\Scripts\python.exe -m pip ...` and `venv\Scripts\python.exe -m uvicorn ...` directly, or use Command Prompt activation.

## Current limitations and future work

- The legacy graph registry loads JSON at startup. Versioned routes load graphs from PostgreSQL when configured. There is no graph editor, hot reload, or multi-process request rate-limit coordination.
- There are no public graph registration/modification endpoints. Versioned service routes use database API keys and rate limiting, while legacy routes retain their original access behavior. Institutional user/role authentication and production audit retention still require deployment integration.
- Floor-plan SVGs, map editing, geometry validation, room search, classroom availability, live closures, and university administrator tooling are outside this API.
- Accessibility data quality depends on the university's survey and verification. An absent measurement is unknown; a route is not a safety guarantee.
- Wheelchair thresholds are optional caller constraints and are not a substitute for individualized needs or local accessibility standards.
- The API returns metadata for a separate navigation guidance system; it does not generate audio instructions or TTS.
- University SSO/RBAC workflows, durable audit-log retention, graph versioning, real-time closures, and route guidance are planned extensions, not implemented features.

## Versioned service API and PostgreSQL

The `/api/v1` routes are intended for private server-to-server access. Every success response has `{ "success": true, "data": ..., "message": "..." }`; errors include `success: false`, `data: null`, and a safe message. Swagger lists legacy and versioned routes at `/docs`.

API keys are stored in PostgreSQL by public prefix and SHA-256 hash. FastAPI checks permission scopes, revocation and expiry, then applies a per-process limit (`AI_RATE_LIMIT_PER_MINUTE`, default 120/minute). Create or revoke keys with `python scripts/api_keys.py`; the unredacted key is shown once and belongs only in a trusted caller's server environment. PostgreSQL is accessed through `data/postgres.py`; university graph data and consented session analytics use this adapter.

| Method | FastAPI path | Permission | Purpose |
|---|---|---|---|
| `GET` | `/api/v1/health` | public | Versioned health envelope |
| `POST` | `/api/v1/navigation/route` | `navigation:route` | Calculate an actual Dijkstra route |
| `GET` | `/api/v1/sessions/consent` | public | Current consent text/version and data handling |
| `POST` | `/api/v1/sessions/start` | `sessions:write` | Start explicit, time-limited sharing |
| `POST` | `/api/v1/sessions/{id}/events` | `sessions:write` | Validate a graph path and persist minimized metrics/unordered edge use |
| `POST` | `/api/v1/sessions/{id}/pause` | `sessions:write` | Pause contribution collection |
| `POST` | `/api/v1/sessions/{id}/resume` | `sessions:write` | Resume before server-enforced expiry |
| `POST` | `/api/v1/sessions/{id}/finish` | `sessions:write` | Stop collection |
| `GET` | `/api/v1/sessions/{id}/status` | `sessions:write` | Check status and expiry with the opaque session token |
| `DELETE` | `/api/v1/sessions/{id}` | `sessions:write` | Delete the session and retained events |

The database graph is used for versioned routing when `DATABASE_URL` is configured; the existing JSON registry remains supported for legacy/local navigation. A trusted application backend should derive a pseudonymous contributor reference. FastAPI stores only its HMAC digest and the hash of the opaque session token. Analysis thresholds remain configurable using `ACCESU_MIN_SESSIONS_PER_GROUP`, `ACCESU_MIN_CONTRIBUTORS_PER_GROUP`, `ACCESU_DISPARITY_RATIO`, and `ACCESU_MIN_DURATION_DIFFERENCE_SECONDS`.

For PostgreSQL-backed `/api/v1` endpoints, apply `migrations/001_initial.sql` and configure `DATABASE_URL`. Create and revoke hashed API keys with `python scripts/api_keys.py`; keep the generated secret on trusted server callers only.

### PostgreSQL setup for the API

The API repository does not bundle a database server or Express gateway. Point it at a PostgreSQL database, then from `ai-service/` apply the schema and create a scoped key:

```powershell
$env:DATABASE_URL = "postgresql://USER:PASSWORD@HOST:5432/DATABASE"
psql $env:DATABASE_URL -f migrations/001_initial.sql
python scripts/api_keys.py create navigation-client --permissions navigation:route
```

Copy the one-time `accu_...` value into the trusted calling backend's secret store. For analytics/session collection, issue a key with the needed scopes, and configure `ACCESU_CONTRIBUTOR_HASH_SECRET` and `ACCESU_CONSENT_VERSION`. Revoke a key by its public prefix:

```powershell
python scripts/api_keys.py revoke 0123456789
```

Populate `buildings`, `floors`, `nodes`, and `edges` with university-verified graph data before calling PostgreSQL-backed `/api/v1/navigation/route`. No fake graph or student activity is inserted automatically. The JSON demo graph remains available for the legacy local navigation endpoints.

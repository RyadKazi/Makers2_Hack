# AccesU Navigation API

AccesU Navigation API is a Python and FastAPI service for calculating routes through university-authored building graphs. It applies Dijkstra's shortest-path algorithm to explicit, verified graph connections and returns the ordered route with floor transitions and map metadata.

> **Navigation is assistive.** This service does not replace a white cane, guide dog, human assistance, or an on-site accessibility inspection. A route result is not a safety guarantee. The included demonstration graph is synthetic and is not a surveyed campus map.

## Features

- Dijkstra routing over a building-level graph spanning multiple floors.
- General pedestrian, wheelchair, and visual-impairment navigation profiles. `blind_navigation` is also accepted as a compatibility profile value.
- Wheelchair constraints that exclude stairs, blocked connections, and graph facts explicitly marked inaccessible. Verified door-width and ramp-slope measurements can be checked against caller-provided thresholds.
- University-defined node IDs, coordinates, floor IDs, doors, rooms, entrances, stairs, elevators, ramps, landmarks, and verified connections.
- Read-only HTTP endpoints for health, building discovery, node lookup, and route calculation.
- Optional startup loading from JSON. Validated graphs are held in memory for the process lifetime; there is no database dependency.
- Swagger UI and OpenAPI schema generated by FastAPI.

The visual-impairment profile returns ordered nodes, edge metadata, floor transitions, and available landmarks. It does not generate spoken directions. A separate guidance layer can use these verified facts to produce instructions.

The router validates HTTP payloads and selects a building graph. `route_service` invokes the navigation modules and assembles the response. FastAPI is not involved in graph construction or path search. No nodes or edges are inferred from coordinates.

## Quick Start for Frontend Developers

### 1. Start the API

From the `ai-service` directory, create and activate a virtual environment, install dependencies, then load the synthetic example graph and start Uvicorn.

**Windows PowerShell:**

```powershell
py -3.11 -m venv venv
.\venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
$env:ACCESU_BUILDINGS_FILE = "examples/demo_building.json"
python -m uvicorn main:app --reload
```

**Linux or macOS:**

```bash
python3 -m venv venv
source venv/bin/activate
python -m pip install -r requirements.txt
export ACCESU_BUILDINGS_FILE=examples/demo_building.json
python -m uvicorn main:app --reload
```

The local base URL is **`http://127.0.0.1:8000`**. Swagger is at [`/docs`](http://127.0.0.1:8000/docs), ReDoc at `/redoc`, and the OpenAPI document at `/openapi.json`.

If `ACCESU_BUILDINGS_FILE` is not set, the service starts with an empty registry. `/buildings` returns an empty list and route requests return `404 Building not found` until a graph is loaded.

### 2. Send a route request

The example graph is synthetic. This request calculates a route from graph data in `examples/demo_building.json`; it is not a real campus route:

```javascript
const response = await fetch("http://127.0.0.1:8000/navigation/route", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    building_id: "SYNTHETIC_DEMO_BUILDING",
    start_node: "GROUND_ENTRANCE",
    destination_node: "F1_ROOM_105",
    profile: "general"
  })
});

const body = await response.json();
if (!response.ok) {
  throw new Error(body.message ?? `Route request failed (${response.status})`);
}

console.log(body.route.nodes); // Ordered university-defined node IDs
console.log(body.route.total_distance); // Sum of edge distances
console.log(body.route.floor_transitions); // Floor changes along the path
```

The API returns node IDs in traversal order, plus `node_details` with coordinates and landmarks and `edges` with connection metadata. A map can draw the route by looking up each returned node's `floor_id`, `x`, and `y` in its own floor-plan layer. Use `floor_transitions` to switch layers or show a transition. Do not draw lines across floors as if they were same-floor corridors.

### 3. Understand errors

Errors use a consistent JSON envelope, for example:

```json
{
  "success": false,
  "message": "no valid route from 'GROUND_ENTRANCE' to 'F1_ROOM_105' for wheelchair profile"
}
```

Handle `response.ok` before rendering route data. A missing building or node returns `404`; invalid JSON fields/profile and a valid request with no accessible route return `422`. See [HTTP endpoints](#http-endpoints) for the complete status behavior.

## HTTP endpoints

| Method | Path | Purpose | Typical errors |
|---|---|---|---|
| `GET` | `/` | Welcome message and service status | — |
| `GET` | `/health` | Health status and loaded building count | — |
| `GET` | `/buildings` | Building IDs and graph counts | — |
| `GET` | `/buildings/{building_id}` | Full validated building, floors, nodes, and edges | `404` unknown building |
| `POST` | `/navigation/route` | Calculate a route against the selected graph | `404` unknown building/node; `422` invalid request or no valid route |
| `GET` | `/navigation/nodes/{node_id}` | Retrieve node information | `404` unknown node/building; `409` ambiguous node ID |

Node IDs are unique within a building, not necessarily across all buildings. Supply `?building_id=BUILDING_A` to disambiguate node lookup when needed.

### Route request

```http
POST /navigation/route
Content-Type: application/json
```

```json
{
  "building_id": "SYNTHETIC_DEMO_BUILDING",
  "start_node": "GROUND_ENTRANCE",
  "destination_node": "F1_ROOM_105",
  "profile": "general",
  "constraints": {}
}
```

`constraints` is optional. It may contain `minimum_door_width_m` and `maximum_ramp_slope`. A measurement is used to filter a route only when its corresponding graph metadata is marked `verified: true`. Unknown measurements are not fabricated. No default door-width or ramp-slope threshold is imposed; clients can send the preferences appropriate to their user and context.

Profiles accepted by the API:

- `general`: shortest valid pedestrian path, including declared stairs.
- `wheelchair`: never uses stairs; excludes blocked and explicitly inaccessible nodes/connections. Verified width and slope data is checked when a threshold is supplied. Equal-distance choices prefer verified accessible entrance, ramp, or elevator connections.
- `visual_impairment`: shortest valid pedestrian path with ordered nodes, transitions, edges, and available landmarks. It does not generate audio instructions.
- `blind_navigation`: compatibility spelling for the same behavior as `visual_impairment`.

Example success response for the synthetic graph. The JSON below shows the core fields; actual responses also include complete `node_details` and `edges` arrays for the returned path.

```json
{
  "success": true,
  "message": "Route successfully calculated",
  "route": {
    "nodes": [
      "GROUND_ENTRANCE",
      "GROUND_CORRIDOR",
      "STAIR_G",
      "STAIR_F1",
      "F1_ROOM_105"
    ],
    "total_distance": 18.0,
    "floor_transitions": [
      {
        "from_floor": 0,
        "to_floor": 1,
        "from_floor_id": "G",
        "to_floor_id": "F1",
        "type": "stairs"
      }
    ],
    "profile": "general"
  }
}
```

The route's node IDs and transition are calculated from the graph in `examples/demo_building.json`; the distance is the sum of its edge distances. The API additionally returns Pydantic node and edge objects, including coordinates and accessibility/landmark metadata.

### Error responses

Validation and HTTP errors use `{ "success": false, "message": "..." }`. Request validation errors also include an `errors` array with field locations. Status codes:

- `404`: requested building or node is not loaded.
- `409`: node ID exists in multiple buildings and `building_id` was omitted.
- `422`: malformed request, unsupported profile, or no valid route for the selected profile.

FastAPI's built-in request validation also rejects unknown request fields and malformed values.

## Building graph data

### How the graph works

- A **building** owns one or more **floors**, each with a stable `floor_id` and display level.
- University staff place each **node** directly on its floor layout. A node includes its building/floor IDs, coordinates, type, and known metadata. Door nodes can be destinations.
- An **edge** represents a verified physical connection between two explicitly named nodes. The service does not connect nearby coordinates automatically. Edges are bidirectional by default; set `bidirectional: false` for one-way movement.
- Corridor and doorway edges must remain on one floor. Cross-floor edges must be explicitly typed as stairs, elevators, or ramps.
- Stair nodes on different floors must have distinct node IDs and share the same `staircase_connection_id`; a stairs edge connects corresponding nodes.
- Elevator edges connect elevator nodes; ramp edges connect ramp nodes. These types can cross floors.
- Edge distances must be finite and non-negative. Blocked edges and nodes are excluded from route results.

The graph describes navigation connectivity separately from the visual floor-plan drawing. This service does not ingest SVG geometry or verify a building survey. The administrator-provided graph must represent real, inspected connections.

### Graph JSON format

Use `examples/demo_building.json` as a complete schema example only. It is explicitly synthetic. A building file can contain a single building object, an array of building objects, or a wrapper object with a `buildings` array. The following is a valid, minimal, single-floor graph shape:

```json
{
  "building_id": "BUILDING_A",
  "name": "Example building; replace with surveyed data",
  "floors": [{"floor_id": "G", "level": 0, "name": "Ground floor"}],
  "nodes": [
    {
      "node_id": "G_ENTRANCE",
      "building_id": "BUILDING_A",
      "floor_id": "G",
      "x": 10,
      "y": 12,
      "node_type": "entrance"
    },
    {
      "node_id": "G_ROOM_105",
      "building_id": "BUILDING_A",
      "floor_id": "G",
      "x": 40,
      "y": 16,
      "node_type": "door",
      "is_destination": true,
      "label": "Room 105"
    }
  ],
  "edges": [
    {
      "source_node": "G_ENTRANCE",
      "destination_node": "G_ROOM_105",
      "distance": 30,
      "connection_type": "doorway"
    }
  ]
}
```

This JSON is structurally valid, but its coordinates and connection are illustrative placeholders and do not describe a real building. Replace them with administrator-provided map data before use. Every referenced node must exist, every node's floor must exist, and all edges must satisfy the model's floor-transition rules. Relevant node types are `door`, `staircase`, `corridor_intersection`, `entrance`, `elevator`, `ramp`, `room_access`, and `waypoint`. Connection types are `corridor`, `doorway`, `stairs`, `elevator`, `ramp`, `entrance`, and `other`.

The initial graph source is a JSON file provided at startup. The service validates it before serving requests and holds the resulting graphs in memory to avoid rebuilding them for every route. No public graph edit endpoint is provided. An authorized admin workflow, durable storage, and PostgreSQL integration are future work; do not expose graph mutation without authentication and authorization.

## How route calculation works

The existing Dijkstra implementation uses each allowed edge's `distance` as its primary cost. It searches the whole building graph, so explicitly linked vertical transitions can participate in one route. It returns the ordered node IDs, oriented traversed edges, total distance, and transitions where the floor changes.

Accessibility filtering happens before an edge is relaxed by Dijkstra. Blocked connections are excluded for all profiles. Wheelchair routes exclude stairs and connections/nodes explicitly marked inaccessible. Optional door-width and ramp-slope constraints apply only to verified measurements. Equal-distance wheelchair routes use a secondary preference for verified accessible entrances, ramps, and elevators; that preference never makes a longer route shorter. No route is returned if the graph has no valid path.

`general` and `visual_impairment` profiles may use stairs when they are declared. Spoken instructions, wall-following guidance, map geometry checks, automatic obstruction detection, route-time estimates, and machine-learning predictions are not implemented.

## Frontend and backend integration

### Next.js / browser JavaScript

Set the browser's API base URL in your frontend configuration and make a JSON request. In production, expose only the appropriate public API URL to browser code; keep internal service URLs in server-side configuration.

```javascript
const API_BASE_URL = process.env.NEXT_PUBLIC_ACCESU_API_URL ?? "http://127.0.0.1:8000";

export async function fetchAccessibleRoute({ buildingId, startNode, destinationNode, profile }) {
  const response = await fetch(`${API_BASE_URL}/navigation/route`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      building_id: buildingId,
      start_node: startNode,
      destination_node: destinationNode,
      profile
    })
  });

  const body = await response.json();
  if (!response.ok) {
    throw new Error(body.message || `Navigation request failed (${response.status})`);
  }
  return body.route;
}

const route = await fetchAccessibleRoute({
  buildingId: "SYNTHETIC_DEMO_BUILDING",
  startNode: "GROUND_ENTRANCE",
  destinationNode: "F1_ROOM_105",
  profile: "general"
});
// Use route.node_details to map returned IDs to floor coordinates.
console.log(route.nodes, route.floor_transitions);
```

The default CORS allowlist permits `localhost:3000` and `127.0.0.1:3000`. Configure `ACCESU_ALLOWED_ORIGINS` for other browser origins. Server-to-server Express calls do not rely on browser CORS.

### Express.js server-to-server call

Keep the FastAPI base URL in the Express server's environment (for example, `ACCESU_NAVIGATION_URL`). The Express application should perform its own user authentication/authorization and send only the route request data needed by this service.

```javascript
const navigationUrl = process.env.ACCESU_NAVIGATION_URL ?? "http://127.0.0.1:8000";

app.post("/api/routes", async (req, res, next) => {
  try {
    // Authenticate and authorize req.user in Express before forwarding.
    const upstream = await fetch(`${navigationUrl}/navigation/route`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        building_id: req.body.building_id,
        start_node: req.body.start_node,
        destination_node: req.body.destination_node,
        profile: req.body.profile,
        constraints: req.body.constraints
      })
    });
    const payload = await upstream.json();
    res.status(upstream.status).json(payload);
  } catch (error) {
    next(error);
  }
});
```

For deployment, restrict network access to the internal navigation service and add the reviewed service-to-service authentication required by the host architecture. This initial service does not implement authentication itself.

## Troubleshooting

- **`Building not found`**: confirm `ACCESU_BUILDINGS_FILE` points to readable JSON and the requested `building_id` matches it exactly. Without the variable, the registry is empty.
- **Startup validation error**: check duplicate IDs, node `building_id`/`floor_id`, edge endpoints, finite non-negative distances, and vertical edge types. Startup fails rather than serving invalid graph data.
- **`start node not found` / `destination node not found`**: verify the IDs belong to the selected building; IDs are case-sensitive.
- **No valid route**: ensure the administrator defined a continuous series of real edges. For wheelchair routes, check for stairs, blocked edges, inaccessible metadata, and configured width/slope constraints. The engine will not invent an alternative connection.
- **Browser CORS error**: add the frontend's exact origin (scheme, hostname, and port) to `ACCESU_ALLOWED_ORIGINS`, then restart the service.
- **HTTPX/TestClient import error**: reinstall dependencies with `python -m pip install -r requirements.txt` in the active virtual environment.
- **PowerShell cannot activate the environment**: use `venv\Scripts\python.exe -m pip ...` and `venv\Scripts\python.exe -m uvicorn ...` directly, or use Command Prompt activation.

## Current limitations and future work

- Building graphs are loaded from one JSON file at startup and held in process memory; there is no database, persistence, hot reload, or multi-process graph synchronization.
- There are no public graph registration or modification endpoints, authentication, authorization, rate limits, or audit logging. Keep the service on a trusted network until those controls are implemented by the deployment architecture.
- Floor-plan SVGs, map editing, geometry validation, room search, classroom availability, live closures, and university administrator tooling are outside this API.
- Accessibility data quality depends on the university's survey and verification. An absent measurement is unknown; a route is not a safety guarantee.
- Wheelchair thresholds are optional caller constraints and are not a substitute for individualized needs or local accessibility standards.
- The API returns metadata for a separate navigation guidance system; it does not generate audio instructions or TTS.
- PostgreSQL-backed storage, authenticated admin workflows, graph versioning, real-time closures, and route guidance are planned extensions, not implemented features.
